# AI 知识定期更新工作流

这个站点不是一次性资料库，而是一个面向 IaaS 架构师转型 AI 架构师的长期知识产品。更新机制要解决三个问题：

1. 新知识从哪里来。
2. 怎么判断它是否值得入库。
3. 入库后如何保证质量、来源和体验。

## 1. 更新节奏

| 节奏 | 更新对象 | 产出物 | 负责人视角 |
| --- | --- | --- | --- |
| 每周 | 模型、推理框架、芯片、云厂商、开源工具 | 1 条知识雷达记录，必要时新增短文或更新原文 | 判断“这条变化是否影响架构选型”。 |
| 每月 | 封装、机柜、网络、存储、推理成本、Agent 工程 | 1 个深度专题或 1 组文章更新 | 判断“这组知识能否形成可学习主线”。 |
| 每季度 | 模块结构、路线顺序、手绘卡片覆盖 | 1 次信息架构复盘 | 判断“当前路线是否仍然适合 IaaS 转 AI 架构”。 |
| 上线前 | 所有新增或修改内容 | build、浏览器检查、移动端检查 | 判断“内容和体验是否可以发布”。 |

## 2. 来源分级

每条新增内容都必须标注来源类型。来源类型决定文章语气和可信度。

| 来源类型 | 示例 | 写法要求 |
| --- | --- | --- |
| 官方 | NVIDIA、AMD、云厂商、框架官方文档 | 可以用于规格、功能、架构描述，但仍要标注发布日期或版本。 |
| 论文 / 标准 | arXiv、ACM、USENIX、OCP、UCIe、PCI-SIG | 可以用于原理和实验结论，需要说明实验边界。 |
| 工程实测 | benchmark、源码分析、部署日志 | 可以用于实践判断，需要说明环境、版本、硬件和限制。 |
| 媒体报道 | Tom's Hardware、SemiAnalysis、The Register 等 | 适合作为供应链、成本、趋势线索，不写成官方事实。 |
| 分析师估算 | Morgan Stanley、Omdia、TrendForce 等 | 只能写成估算或线索，必须标注“非官方 BOM / 非官方报价”。 |

## 3. 入库判断

一条新信息不应该因为“新”就进入站点。入库前先问 5 个问题：

1. 它是否影响 AI 架构师的成本、容量、性能、稳定性或治理判断？
2. 它应该落在哪个模块：硬件、集群运维、云原生平台、推理系统、RAG/Agent，还是工具？
3. 它是独立短文，还是应该并入已有专题？
4. 它需要手绘卡片解释吗？
5. 它是否有足够可靠的来源支撑？

## 4. 每篇新增内容的必填清单

| 字段 | 要求 |
| --- | --- |
| 来源链接 | 至少 1 个主要来源，重要数字需要直接来源。 |
| 更新时间 | 写入 frontmatter `date` 或正文“数据截至”。 |
| 可信度标签 | 官方 / 论文 / 工程实测 / 媒体 / 分析师估算。 |
| 对 IaaS 架构师的影响 | 明确说明对资源池、网络、存储、SRE、成本或平台治理的迁移意义。 |
| 所属模块 | 必须能被导航发现，不做孤立文章。 |
| 验收证据 | build 通过、本地浏览器检查通过、移动端无页面级横向溢出。 |

## 7. 当前优先更新主题

| 优先级 | 主题 | 原因 | 推荐落点 |
| --- | --- | --- | --- |
| P0 | NVIDIA NVL 机柜成本拆解 | 直接影响 AI Infra 成本、供电、液冷和部署密度判断 | 硬件架构 / 先进封装专题 |
| P0 | 推理成本与 KV Cache 容量 | 直接影响推理服务 SLO 和成本模型 | 推理系统 |
| P1 | Agent 工程与 MCP 工具治理 | 影响应用架构、权限、安全和平台边界 | 智能体系统 |
| P1 | 云厂商 GPU 实例与网络规格 | 影响 IaaS 架构师的采购、容量和迁移判断 | AI 集群运维 / 云原生 AI 平台 |
| P2 | 模型发布与上下文窗口变化 | 影响 RAG、Agent 和推理容量，但需要过滤营销噪音 | LLM 理论与基础 / 推理系统 |

## 8. 上线前强制门禁

每次更新站点，都必须完成：

```bash
npm run build
```

还必须用本地浏览器检查：

- 首页关键入口存在。
- 被更新的模块页可打开。
- 新增或修改的文章页可打开。
- 移动端没有页面级横向溢出。
- 如果浏览器工具断开或失败，不能把工作标记为最终完成。
